## What is this?

Wonnet is an email client that feels instant. The apps read and write a local SQLite copy of the
mail; our server syncs with the providers (Gmail, Outlook and JMAP) and keeps the apps' copies current over
a WebSocket. It looks like the old Newton Mail: calm, plain, nothing that isn't needed.

| Folder | What it is |
| --- | --- |
| `apps/server` | The `mail-server` binary: Rust, axum, sqlx on Postgres |
| `crates/core` | The local copy, the link to the server and all rendering, linked into every app |
| `crates/protocol` | What the server and the core agree on: types, ops, the sync socket's messages |
| `packages/apple` | `MailUI`, the Swift package both apps are made of |
| `apps/macos`, `apps/ios` | The app shells; the iOS Xcode project is generated by XcodeGen, never committed |
| `apps/android` | The Android app: Kotlin and Jetpack Compose; `core` is the core's JNI library |
| `apps/gpui` | The Windows and Linux app: Rust and GPUI, its own Cargo workspace |
| `packages/theme` | `tokens.json`, the source of every colour, opacity, radius and shadow |
| `apps/marketing` | wonnet.app (Astro); `src/components/demo` is a React copy of the Mac app |

## Things that aren't obvious from the code

- The server and the core apply the same `Op` function (`crates/protocol/src/ops.rs`). Bump
  `PROTOCOL_VERSION` in `wire.rs` when an old app or server could no longer understand the other.
- Every write to synced rows on the server runs in `UserTx` (`db.rs`), which keeps a user's revs in
  order. The server runs one replica: an account's worker must run in one place.
- The core's `core.rs` is one loop that owns all state; anything that waits on the network runs in a
  task and sends its result back. Its SQLite store is a cache: a new schema rebuilds it.
- `DEV_LOGIN=1` gives a session without an account, for tests and local work only. The apps'
  `--demo` shows made-up mail (`crates/core/src/demo.rs`) and never connects.
- The marketing site's demo follows the Mac app: a change to how the Mac app looks changes it too.
- There are four apps: Mac, iOS, Android and desktop (`apps/gpui`, Windows and Linux). Android
  follows the iOS app and the desktop app follows the Mac app; each is written on its own, so a
  feature or a look lands in every app in the same change.
- The Mac, desktop and Android apps update themselves from the latest GitHub release, which
  `release.yml` makes on every push to main: `Wonnet.zip`, `Wonnet.apk`,
  `Wonnet-windows-x86_64.zip` and `Wonnet-linux-<arch>.AppImage`. Renaming an asset breaks the
  updates of every copy already installed.
- Android's push goes through Firebase, iOS's through APNs; both are sealed with the device's key.
  The APK must always be signed with the same key, or installed copies can no longer update. The
  desktop app installs only updates signed with `DESKTOP_UPDATE_KEY`, whose public half it holds.
- The desktop app draws mail in the system's web view: WebView2 on Windows, WebKitGTK on Linux.
  On Linux it runs on X11 (XWayland on a Wayland desktop), as WebKitGTK can only be laid into an
  X11 window. The AppImage carries WebKitGTK 4.1 and GTK (`build-linux.sh`), so nothing needs
  installing; what every desktop has (glibc, graphics drivers, X11, fonts, GnuTLS) it takes from
  the system.
- The desktop app builds on GPUI and wgpu with patches of ours, so that Linux redraws and presents
  only what changed in a frame: `apps/gpui/patches` holds a `.patch` for each crate, and
  `scripts/patch-crates.sh` unpacks the crates with them into `patched/`, which
  `[patch.crates-io]` points at. Run it before `cargo`; the scripts and CI do. To change a patch,
  edit its crate in `patched/`, then run `scripts/patch-crates.sh --save`. Another GPUI or wgpu
  needs the patches redone for its versions in `patches/crates`; the script refuses a patch that
  `Cargo.lock` left unused.
- Production is the `Wonnet` project on Unbind; a push to `main` deploys what it touches. When a
  deploy changes required variables, deploy the code first and change the variables after: Unbind
  restarts the service on every variable change.

## General Rules:

- Keep it simple. Do not overcomplicate things.
- The apps must never wait on the network. Every action reads and writes the local copy and the
  server catches up. Nothing slow runs on the main thread.
- Rendering logic belongs in `crates/core`, not in an app, so that every future app gets it.
- Every app does the same things. What one gets, the others get in the same change. What the
  Apple apps share is written once, in `packages/apple/Sources/MailUI/Shared`.
- A button, a field or a toast in the apps comes from the app's own set of controls
  (`Shared/Views/UI` for Apple). A view does not style a control by hand; what is missing is
  added to the component. The rules (sizes, spacing, hover, pending, sheets, errors) are in
  `packages/apple/DESIGN.md` and hold for every app.
- Colours, opacities, radii and shadows come from `packages/theme/tokens.json`, never a hex value
  or a number of a view's own. Text sizes come from `TextStyle`, distances from `Space`.
- The server holds people's mail. Credentials are sealed, tokens hashed, and a sign-in code
  works once and only with its secret. Anything that changes this needs a test in
  `apps/server/src/e2e`.
- Do not leave paragraphs of comments on top of the code. Prefer clear names; keep the comments
  that are needed concise. Comments move with the code.
- Use guard statement patterns in any code you write.
- Do not edit generated code: `Cargo.lock`, `packages/theme/tokens.css`, `Tokens.swift`,
  `AccountColors.swift`, `Tokens.kt`, `apps/gpui/src/theme/tokens.rs` (change `tokens.json` and
  run `node packages/theme/build.mjs`). Never
  edit an applied migration in `apps/server/migrations`; add a new one.
- Do not write useless tests; tests cover input/output behaviour.
- Reinvent the wheel but do not reinvent the car. A simple problem gets no new library; a
  complex but common one probably has a modern library already.
- Do not insert yourself into our code, commits or PRs in any way.
- Never commit or push unless asked to.
- After you make code changes, run the checks below and fix what they raise. Skip the checks and
  the build for a change you are sure breaks nothing, like a single number (a padding, an offset).

## Development

Needs Rust stable, Docker (for Postgres and Stalwart), Node 24 and pnpm. The Apple apps need a
Mac with Xcode; the iOS app also XcodeGen and `rustup target add aarch64-apple-ios
aarch64-apple-ios-sim`. The Android app needs JDK 21, the Android SDK and NDK, `cargo-ndk` and
`rustup target add aarch64-linux-android x86_64-linux-android`. The desktop app builds on any of
the three systems; on Linux it needs the packages `.github/workflows/desktop.yml` installs.

    docker compose up -d                          # Postgres on 5441, Stalwart on 8441
    cargo run -p mail-server -- seed              # demo@example.com with a few hundred messages
    cargo run -p mail-server                      # with the variables of .env.example exported
    cd apps/marketing && pnpm install && pnpm dev # the marketing site
    apps/macos/scripts/build-app.sh --open        # the Mac app
    open apps/macos/build/Wonnet.app --args --demo  # the Mac app with made-up mail, no server
    cd apps/ios && xcodegen generate && open Mail.xcodeproj
    cd apps/android && ./gradlew installDebug    # the Android app, on a running emulator or phone
    adb shell am start -n app.wonnet.wonnet/app.wonnet.MainActivity --ez demo true  # Android with made-up mail
    apps/gpui/scripts/patch-crates.sh && cargo run --manifest-path apps/gpui/Cargo.toml -- --demo  # the desktop app with made-up mail

Checks (`cargo test` needs the compose services; the Stalwart test runs when `STALWART_URL` is set):

    export DATABASE_URL=postgres://mail:mail@localhost:5441/mail STALWART_URL=http://localhost:8441
    cargo fmt --all && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace
    node packages/theme/build.mjs --check
    cd apps/marketing && pnpm check && pnpm build
    cd apps/gpui && scripts/patch-crates.sh && cargo fmt && cargo clippy --all-targets -- -D warnings && cargo test
    cd apps/android && ./gradlew lint assembleDebug

## Commit Messages

Commit messages start with the part of the system they touched, followed by a short imperative
sentence describing the change:

    server: Refuse a sign-in code that was started by another app
    core: Fold quoted text in plain text mail
    core | apple: Show when a send failed

The parts are the folders in `apps`, `crates` and `packages`: `server`, `marketing`, `macos`,
`ios`, `android`, `gpui`, `core`, `protocol`, `apple` and `theme`. Use `ci` for the workflows and `docs` for README.md
and AGENTS.md.

The title should be concise. The description explains the work in more detail (only if
required) while still being concise. Use simple language, do not try to sound smart.
